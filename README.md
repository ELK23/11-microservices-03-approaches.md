# Задание 1
# GitLab CI/CD + Docker
### Для обеспечения процесса разработки с хранением исходного кода, CI/CD и соответствием всем требованиям предлагается следующая комбинация инструментов:
### 1. Система контроля версий и хостинг репозиториев: GitLab
- Облачная система: GitLab SaaS (gitlab.com) или self-hosted (GitLab CE/EE).
- Git-репозитории: Поддержка Git, репозиторий на каждый сервис.
- Триггеры сборки:
    - По событию (push, merge request, tag).
    - По кнопке (ручной запуск с параметрами через variables в .gitlab-ci.yml).

### 2. Непрерывная интеграция и поставка: GitLab CI/CD
- Запуск сборки по событию: Настроить в .gitlab-ci.yml (например, rules, only/except).
- Параметризованные сборки: Через variables в UI или API.
- Настройки на сборку:
    - Переменные окружения (включая masked variables для секретов).
    - CI/CD templates для шаблонов конфигураций.
- Несколько конфигураций из одного репозитория: Использование include и extends в .gitlab-ci.yml.
- Кастомные шаги: Определение своих stages и jobs.
- Параллельные сборки и тесты: Настройка parallel в джобах.

### 3. Безопасное хранение секретов
- GitLab Protected Variables (шифруются в базе).
- HashiCorp Vault (интеграция через GitLab CI).

### 4. Сборка проектов в Docker
- Собственные образы для сборки:
  - Использование image в .gitlab-ci.yml.
  - Возможность загружать свои образы в GitLab Container Registry.
- Docker-in-Docker (dind) для сборки и публикации образов.

### 5. Запуск агентов на своих серверах: GitLab Runner
- Self-hosted раннеры:
    - Развертывание на собственных серверах (Docker, Kubernetes, shell).
    - Поддержка автоскейлинга через Docker Machine или Kubernetes.
- Параллельные сборки: Настройка concurrent в config.toml раннера.
- Развертывание приложений через Helm или GitLab Auto DevOps.

## Обоснование выбора
- GitLab покрывает все требования из списка:
    - Git-репозитории + CI/CD в одной платформе.
    - Гибкость конфигурации через .gitlab-ci.yml.
    - Поддержка Docker и Kubernetes.
- Безопасность: Встроенное управление секретами, интеграция с Vault.
- Масштабируемость: Self-hosted раннеры позволяют запускать сборки на своих серверах.
- Параллелизм: Поддержка параллельных джобов и тестов.
- Шаблоны и кастомизация: include, extends, переменные.

# Задание 2

Решение для сбора и анализа логов в микросервисной архитектуре
Для удовлетворения всех требований предлагается следующая комбинация инструментов:
- Fluent Bit – для сбора и отправки логов (агент на каждом хосте).
- Kafka – в качестве буфера для гарантированной доставки.
- Elasticsearch – для хранения и индексации логов.
- Kibana – для визуализации, поиска и фильтрации логов.
- Fluentd (опционально) – для дополнительной обработки перед отправкой в Elasticsearch.

Схема работы:
Микросервисы (stdout) → Fluent Bit (сбор) → Kafka (буфер) → Fluentd (обработка) → Elasticsearch (хранилище) → Kibana (UI)
Обоснование выбора:
1. Сбор логов: Fluent Bit
- Легковесный агент, минимальные требования к ресурсам.
- Поддержка сбора логов из stdout (например, из Docker-контейнеров).
- Гибкость в парсинге и фильтрации логов.
- Может отправлять данные в Kafka, Elasticsearch или Fluentd.

2. Гарантированная доставка: Kafka
- Работает как буфер, предотвращая потерю логов при перегрузке Elasticsearch.
- Поддержка репликации и высокой доступности.
- Возможность повторной обработки логов при необходимости.

3. Хранение и поиск: Elasticsearch
- Оптимизирован для полнотекстового поиска и фильтрации.
- Масштабируемость и поддержка распределённого хранения.
- Интеграция с Kibana.

4. Визуализация и UI: Kibana
- Удобный интерфейс для разработчиков.
- Возможность сохранения поисковых запросов и создания дашбордов.
- Поддержка ссылок на сохранённые поиски (shareable links).

5. Обработка логов (опционально): Fluentd
- Если требуется сложная обработка (например, обогащение логов метаданными), можно добавить Fluentd между Kafka и Elasticsearch.
- Поддержка плагинов для трансформации данных.

Альтернативы:
- Loki + Grafana (если нужен более легковесный вариант, чем Elasticsearch):
- Loki – для хранения логов (менее ресурсоёмкий, но без полноценного полнотекстового поиска).
- Grafana – для визуализации (поддерживает ссылки на сохранённые поиски).
- Splunk (если бюджет позволяет): Готовое коммерческое решение с мощным поиском и UI.

Итог:
Предложенный стек (Fluent Bit → Kafka → Elasticsearch → Kibana) обеспечивает:
- Сбор логов из stdout с минимальными требованиями.
- Гарантированную доставку через Kafka.
- Мощный поиск и фильтрацию в Elasticsearch.
- Удобный UI с возможностью делиться ссылками на поиски (Kibana).
- Масштабируемость для микросервисной архитектуры.
